# Roadmap проекта

Этот документ фиксирует технические планы развития проекта Proxmox + Terraform + Ansible + K3s. Он нужен как рабочий backlog: чтобы новые задачи не терялись, имели понятный приоритет и были связаны с архитектурными решениями проекта.

## Цели развития

- Разделить инфраструктурный слой, конфигурирование ОС и deployment приложений.
- Подготовить отдельную VM для сервисов, которые не должны запускаться внутри K3s.
- Сделать кластер пригодным для лабораторной эксплуатации: мониторинг, логирование, backup, управление секретами.
- Постепенно приблизить проект к production-like подходу без чрезмерного усложнения домашней инфраструктуры.

## Приоритеты

| Приоритет | Направление | Ценность |
|---|---|---|
| P0 | Стабильный Terraform/Ansible workflow | Воспроизводимое создание VM и K3s-кластера |
| P1 | Vault как внешний сервис | Единое хранилище секретов и внутренний центр сертификации |
| P1 | Backup и восстановление | Возможность восстановить state, кластер и критичные данные |
| P2 | Helm charts | Стандартизированный запуск приложений в K3s |
| P2 | Observability | Метрики, логи и диагностика кластера |
| P3 | GitOps | Автоматизация доставки приложений и конфигураций |

## 1. Standalone VM для Vault

### Задача

Создать отдельную VM вне K3s-кластера для HashiCorp Vault и вспомогательных систем, которые пока не планируется запускать в Kubernetes.

### Почему вне K3s

- Vault должен быть доступен до развертывания приложений в кластере.
- Vault может использоваться как внешний источник секретов для Ansible, Helm и будущих workloads.
- Отдельная VM уменьшает зависимость базовой security-инфраструктуры от состояния Kubernetes.

### План работ

- Раскомментировать и адаптировать `standalone_vms` в `terraform/terraform.tfvars`.
- Добавить Ansible inventory/group для standalone VM или отдельный inventory, если сервисы не должны смешиваться с K3s.
- Создать роль `vault`.
- Настроить storage path, systemd unit и базовую hardening-конфигурацию.
- Описать процедуру init/unseal.
- Настроить backup Vault data.

### Критерии готовности

- Terraform создает VM `vault-1` без влияния на K3s inventory.
- Ansible устанавливает и запускает Vault идемпотентно.
- Vault доступен по HTTPS.
- Документирована процедура восстановления.

## 2. Vault как хранилище секретов и центр сертификации

### Задача

Использовать Vault как единый источник секретов и внутренний CA.

### План работ

- Включить KV secrets engine для инфраструктурных секретов.
- Вынести чувствительные значения из `.env`, `terraform.tfvars` и Ansible vars там, где это практически оправдано.
- Настроить PKI secrets engine для внутреннего CA.
- Выпускать внутренние TLS-сертификаты для сервисов.
- Подготовить Ansible lookup/integration для чтения секретов из Vault.

### Критерии готовности

- Новые сервисы не требуют хранения секретов в Git.
- Есть documented workflow для записи, чтения и ротации секретов.
- Есть базовая политика доступа для администратора и automation-пользователя.

## 3. Helm charts для приложений

### Задача

Создать структуру Helm charts для запуска прикладного и инфраструктурного софта в K3s.

### Целевые приложения

- Python web application: Django или FastAPI.
- Система логирования.
- Система мониторинга.
- AWX или Rundeck для automation-задач.

### План работ

- Создать директорию `helm/`.
- Подготовить общий chart template для stateless web-приложений.
- Добавить values для dev/lab окружения.
- Описать ingress, service, deployment, configmap и secret integration.
- Подготовить отдельные charts или dependency-based values для инфраструктурных сервисов.

### Критерии готовности

- Приложение разворачивается командой `helm upgrade --install`.
- Настройки окружения вынесены в `values.yaml`.
- Секреты не хранятся открытым текстом в chart.

## 4. Observability: мониторинг и логирование

### Задача

Добавить базовую наблюдаемость K3s-кластера и приложений.

### Мониторинг

- Prometheus или kube-prometheus-stack.
- Grafana dashboards.
- Node exporter.
- Kube-state-metrics.

### Логирование

- Loki + Promtail или альтернативный lightweight stack.
- Сбор логов с workload pods.
- Retention policy под ограниченный SSD.

### Критерии готовности

- Видны CPU, RAM, disk, network по node и pod.
- Есть dashboard общего состояния кластера.
- Логи приложений доступны из единого интерфейса.

## 5. Backup и disaster recovery

### Задача

Зафиксировать и автоматизировать backup критичных данных.

### Что нужно бэкапить

- `terraform/terraform.tfstate`.
- Vault data.
- K3s datastore.
- Kubeconfig и cluster token.
- Persistent volumes важных приложений.

### План работ

- Описать локальный backup workflow.
- Добавить автоматизированные backup playbooks.
- Проверить restore на чистой инфраструктуре.
- Документировать RPO/RTO для лабораторного окружения.

### Критерии готовности

- Есть команда или playbook для backup.
- Есть проверенная процедура restore.
- State и секреты не теряются при пересоздании VM.

## 6. GitOps

### Задача

Перейти от ручного запуска Helm к декларативной доставке приложений.

### Возможные инструменты

- Argo CD.
- Flux CD.

### План работ

- Выбрать GitOps-инструмент.
- Разделить репозитории или директории на infrastructure и applications.
- Описать bootstrap GitOps.
- Настроить sync policy для lab-окружения.

### Критерии готовности

- Новое приложение появляется в кластере после merge в Git.
- Drift между Git и кластером виден в UI/CLI.
- Есть rollback-процедура.

## 7. Security hardening

### Задача

Постепенно усилить безопасность VM, Ansible и K3s.

### План работ

- Ограничить SSH-доступ только ключами.
- Проверить права пользователя `victor`.
- Добавить firewall rules для VM.
- Ограничить доступ к Kubernetes API.
- Настроить RBAC для пользователей и automation.
- Проверить политику хранения kubeconfig.
- Добавить регулярную ротацию токенов и сертификатов там, где это оправдано.

### Критерии готовности

- SSH password auth отключен.
- Административные kubeconfig и Vault token не хранятся в Git.
- Доступы описаны и минимизированы.

## 8. Улучшение качества проекта

### Задачи

- Добавить `ansible-lint`.
- Добавить pre-commit hooks для Terraform и Ansible.
- Добавить `terraform validate` и `ansible-playbook --syntax-check` в единый quality workflow.
- Документировать правила изменения Terraform state.
- Рассмотреть remote backend для Terraform state.

### Критерии готовности

- Перед изменениями можно запускать одну команду проверки.
- Ошибки форматирования и синтаксиса ловятся до `apply`.
- Документация отражает фактическую структуру проекта.

## Ближайший рекомендуемый порядок работ

1. Завершить стабильный workflow `make deploy`, `make destroy`, `make ansible`.
2. Добавить standalone VM `vault-1`.

7. Развернуть logging stack.
